Redesign OrdinalNumber to handle arbitrary fast-growing hierarchy levels
========================================================================

PROBLEM:
Current OrdinalNumber has hardcoded layers:
- Layer 0: Number (up to 10^12)
- Layer 1: {mantissa, exponent} - scientific notation (up to 10^308)
- Layer 2: {tower: [a]} - tower notation (10^10^a)

Each layer requires ~200 lines of custom code for add/mul/compare/format.
The game naturally produces ARBITRARY layers via auto-upgrader chains:
- auto_train → tower grows (layer 2)
- auto_auto_train → tower growth accelerates (layer 2-3)
- auto_auto_auto_train → approaches layer 3-4
- Each new auto tier = next level in fast-growing hierarchy

INSIGHT - FAST GROWING HIERARCHY:
f0(n) = n+1
f1(n) = 2n (addition iterated)
f2(n) = 2^n (multiplication iterated) ← our layer 1
f3(n) = 2^^n = 2^2^...^2 (exponentiation iterated) ← our layer 2
f4(n) = 2^^^n (tetration iterated)
f5(n) = ...

Game auto-upgrader chains naturally climb this hierarchy!

SCOPE:
- Handle arbitrary FINITE arrow counts with NO per-layer hardcoding
- One set of operations works for ALL levels
- ω-level (infinite ordinals) is a FUTURE goal when game mechanics support it

KEY INSIGHT (from prototype testing):
- Current Tower and Arrow notations collapse to same thing: (arrows, height)
- The game's non-uniform structure (sums + exponentiations) doesn't matter
  because we approximate anyway - larger terms dominate
- We DON'T need a fundamental redesign, just make height RECURSIVE

PROPOSED SOLUTION - RECURSIVE HEIGHT:

```javascript
{
  arrows: Number,         // finite: 0, 1, 2, 3... (not reaching ω yet)
  height: OrdinalNumber   // RECURSIVE - can itself be {arrows, height}
}
```

Examples:
- 10^100         = {arrows: 1, height: 100}
- 10^10^100      = {arrows: 1, height: {arrows: 1, height: 100}}
- 10↑↑5          = {arrows: 2, height: 5}
- 10↑↑↑5         = {arrows: 3, height: 5}
- 10↑↑(10↑↑100)  = {arrows: 2, height: {arrows: 2, height: 100}}

CRITICAL INSIGHT - NORMALIZATION:

Arrows and height TRADE OFF. These are equivalent:
  {arrows: k, height: 10} ≈ {arrows: k+1, height: 1}

Because 10^10 = 10^10 (tautology when you expand the tower).

This means "compare arrows first" is WRONG without normalization:
  {arrows: 2, height: 100} = 10^10^100 = 10^(googol)
  {arrows: 3, height: 1}   = 10^10^10  = 10^(10 billion)
  The FIRST is bigger despite fewer arrows!

SOLUTION: Normalize to keep height in range [1, 10):

```javascript
normalize(a) {
  // Height too big -> increment arrows
  while (a.height >= 10) {
    a.arrows += 1;
    a.height = Math.log10(a.height);  // or recurse if height is OrdinalNumber
  }
  // Height too small -> decrement arrows
  while (a.height < 1 && a.arrows > 0) {
    a.arrows -= 1;
    a.height = Math.pow(10, a.height);
  }
  return a;
}
```

GENERIC OPERATIONS (no per-layer code!):

```javascript
compare(a, b) {
  a = normalize(a);
  b = normalize(b);
  if (a.arrows != b.arrows) return a.arrows - b.arrows;
  return compare(a.height, b.height);  // recurse if height is OrdinalNumber
}

add(a, b) {
  return compare(a, b) > 0 ? a : b;  // take max (approximation)
}

exp10(a) {
  return normalize({arrows: a.arrows + 1, height: a.height});
}

format(a) {
  a = normalize(a);
  if (a.arrows == 0) return a.height.toString();
  if (a.arrows == 1) return "10^" + format(a.height);
  return "10↑^" + a.arrows + " " + format(a.height);
}
```

This handles ALL finite arrow levels with ONE implementation.
The key is normalize() which keeps height in [1, 10) by trading with arrows.

RECURSIVE OPERATIONS:

Comparison (most important for game):
1. Compare arrow count first
2. If equal, recursively compare height
3. Accept approximation at high levels

Addition:
- If arrows differ by >1, return larger
- If arrows equal, result is roughly max(a,b) (like now)
- May need to promote arrow count

Multiplication:
- 10↑k(a) × 10↑k(b) ≈ 10↑k(a+b) for same arrow count
- Different arrow counts: return larger

Display:
- arrows=1: scientific "1.23e45"
- arrows=2: "10^^123" or "10^10^...^10 (123)"
- arrows=3: "10^^^45"
- Or use ordinal names: ε₀, ω, etc. for very high

CHALLENGES:
1. Recursion depth - need base case (arrows=0, height=Number)
2. Operations are approximate - comparison must still be reliable
3. Display needs to be readable at high levels
4. Performance - deep recursion could be slow (probably fine for game)
